# Діагностика Radio 345

Перевірка поточного стану не замінює тривалого прогону на ефірі. Діагностика
не змінює фільтри, номери, словесні правила та затримки повторів.

## Перевірка без зупинки приймача

```bash
.venv/bin/python diagnose_radio345.py --verify-backup --network
```

Без прапорців виконуються перевірка SQLite, розбір локальних `radio*.log` та
читання наявного знімка метрик. Команда не імпортує MLX, не відкриває мікрофон,
не змінює offset і не викликає `getUpdates`. Звіт містить лічильники, версії
оточення та ознаки помилок без текстів, аудіо, ID користувачів чи токенів.
Технічні ключі JSON залишаються стабільними англійською мовою.

SQLite відкривається з `mode=ro` та `query_only=ON`. Перевіряються цілісність,
зовнішні ключі, відповідність голосів підтвердженням, конфлікти активних правил,
посилання на події, очікування виправлень, тимчасові фрази, незавершені видалення
та heartbeat. Прострочені рядки можуть фізично залишатися до штатного очищення;
це не означає пошкодження бази. Голоси `mem:` мають залишатися після закінчення
строку фрази — це накопичене навчання.

`--verify-backup` створює приватну тимчасову копію SQLite, перевіряє її цілісність
і кількість записів, після чого видаляє її. Це перевірка механізму відновлення,
а не налаштування регулярного резервного копіювання.

`--network` виконує тільки GET до локального API, HTTPS API з Mini App і Telegram
`getMe`. Для API очікується 401 без авторизації, для Telegram — 200 та `ok=true`.
Одна успішна проба не доводить стабільності мережі. Повідомлення не надсилаються.
`.env` читається локально, токен не потрапляє до звіту.

`diagnostics-report.json` і `diagnostics.json` виключено з Git. Код виходу 1 означає
помилку БД, копії чи мережевої проби; історичні попередження самі по собі не
встановлюють код помилки. Зупинені служби очікувано не пройдуть мережеві перевірки.

## Робочі метрики

Після перезапуску оновленого `radio.py` створюється приватний `diagnostics.json`
з правами 0600. Він атомарно оновлюється приблизно кожні 30 секунд через heartbeat
і при завершенні. Помилка запису метрик не зупиняє приймання. Кожен запуск має
окрему сесію; перевіряйте `updated_at`/`age_s`, щоб не прийняти старий знімок за
поточний стан. Звичайні журнали застосунку можуть містити тексти ефіру і є приватними.

| Метрики | Значення |
| --- | --- |
| `telegram.*.attempts`, HTTP-коди | Спроби запитів, включно з повторами |
| `api_confirmed/api_rejected` | Прийняття або відмова Telegram, а не прочитання оператором |
| `delivery_uncertain` | Надсилання обірвалося; без відповіді можливі і втрата, і дубль |
| `queue_wait`, `queue_depth`, `queue_overflow` | Очікування, розмір та переповнення черги |
| `queue_discarded_off`, `notify_after_shutdown`, `shutdown_pending` | Явно спостережувані пропуски та незавершені надсилання |
| `ogg_conversion`, `conversion_failed`, `text_fallback`, `voice_exhausted` | Конвертація й резервний текст |
| `update_processing_error`, `update_quarantined`, `quarantine_write_failed` | Помилки команд і необхідність перевірки карантину |
| `duplicate_update_skipped` | Повторне вже підтверджене оновлення |
| `asr.whisper`, `asr.qwen`, `asr.correction_pipeline` | Тривалість етапів |
| `models.*`, `workers.*`, `audio.*` | Моделі, потоки, перезапуски й витіснення з аудіочерг |
| `asr.*_filtered`, `asr.low_rms`, `llm.rejected_*`, `llm.generation_error` | Причини відхилення або помилки |

Затримки містять середнє й максимум за сесію та p95 останніх 128 вимірювань.
Long polling `getUpdates` близько 30 секунд є штатним очікуванням, а не затримкою
надсилання. Відмова Qwen не дорівнює помилці — консервативна перевірка зберігає
початковий варіант. Різниця кількості запитів і повідомлень може пояснюватися
режимом OFF, командами бота, повторами та резервним текстом.

`TG_DIAG` у журналі містить операцію, знеособлений результат і час запиту.
`connection_reset` визначається зі структури винятку без запису його тексту
в діагностичні метрики. Аналіз історичних журналів підтримує старі російські
та нові українські повідомлення.

## Тривала перевірка

1. Перезапустіть служби через `start_radio345.py`, не запускаючи другий приймач.
2. Зберіть 24 години звичайного навантаження, локально архівуючи знімки метрик.
3. Перевірте затримки, черги, HTTP 429/5xx, обриви з’єднань, перезапуски й втрати кадрів.
4. Вручну зіставте кілька реальних повідомлень із Telegram: агрегати не доводять
   повноти доставки. Не надсилайте синтетичні повідомлення в робочий чат заради тесту.
5. Для оцінки Whisper потрібні аудіо й перевірені еталонні тексти; самі лічильники
   не дають WER або оцінки коротких позивних. Зміни фільтрів і повторів робіть
   після вимірювань та окремих тестів.

Автоматичні перевірки: `.venv/bin/python -m pytest -q` і
`node --test tests/miniapp.test.cjs`. Вони перевіряють транзакції, відновлення,
безпеку чисел і позивних та знеособлення діагностики на тимчасових даних,
але не вимірюють якість живої MLX-моделі.
