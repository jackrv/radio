# Діагностика Radio 345

Перевірка поточного стану не замінює тривалого прогону на ефірі. Діагностика
не змінює фільтри, номери, словесні правила та затримки повторів.

## Перевірка без зупинки приймача

```bash
.venv/bin/python diagnose_radio345.py --verify-backup --network
```

Без прапорців виконуються перевірка SQLite, розбір локальних `radio*.log` та
читання наявного знімка метрик. Команда не імпортує MLX, не відкриває мікрофон,
не змінює offset і не викликає `getUpdates`. Звіт містить лічильники, версії
оточення та ознаки помилок без текстів, аудіо, ID користувачів чи токенів.
Технічні ключі JSON залишаються стабільними англійською мовою.

SQLite відкривається з `mode=ro` та `query_only=ON`. Перевіряються цілісність,
зовнішні ключі, відповідність голосів підтвердженням, конфлікти активних правил,
посилання на події, тимчасові фрази, незавершені видалення
та heartbeat. Прострочені рядки можуть фізично залишатися до штатного очищення;
це не означає пошкодження бази. Голоси `mem:` мають залишатися після закінчення
строку фрази — це накопичене навчання.

`--verify-backup` створює приватну тимчасову копію SQLite, перевіряє її цілісність
і кількість записів, після чого видаляє її. Це перевірка механізму відновлення,
а не налаштування регулярного резервного копіювання.

`--network` виконує тільки GET до локального API, HTTPS API з Mini App і Telegram
`getMe`. Для API очікується 401 без авторизації, для Telegram — 200 та `ok=true`.
Одна успішна проба не доводить стабільності мережі. Повідомлення не надсилаються.
`.env` читається локально, токен не потрапляє до звіту.

`diagnostics-report.json` і `diagnostics.json` виключено з Git. Код виходу 1 означає
помилку БД, копії чи мережевої проби; історичні попередження самі по собі не
встановлюють код помилки. Зупинені служби очікувано не пройдуть мережеві перевірки.

## Робочі метрики

Після запуску `radio.py` створюється приватний `diagnostics.json` з правами 0600.
Він містить останній знімок для сумісності з API, панеллю та командою діагностики.
Одночасно кожна сесія має власний файл у `.local-diagnostics/`:

```text
.local-diagnostics/<початок-UTC>-<session_id>.json
```

Один файл сесії атомарно оновлюється приблизно кожні 30 секунд через heartbeat
і при завершенні. Це знімки агрегатів, а не необмежений журнал кожного сегмента.
Середні, максимуми й лічильники охоплюють сесію; p95 і докладні сегменти, як раніше,
охоплюють останні 128 вимірювань. Тексти, аудіо й токени не додаються.

Перед заміною попереднього `diagnostics.json` новим запуском старий валідний знімок
переноситься в історію. Новіший архівний знімок не замінюється старішою копією.
Якщо попередню сесію не вдалося заархівувати через помилку диска/доступу,
її єдиний останній знімок не перезаписується; збереження повторюється пізніше.
Це може тимчасово залишити `diagnostics.json` застарілим — перевіряйте час знімка.

Архів не залежить від успішного оновлення heartbeat у SQLite. Помилки запису
діагностики журналюються й не зупиняють приймання. Якщо не вдалося записати лише
один із двох файлів, другий усе одно зберігається. Каталог приватний (0700),
JSON-файли — 0600; `.local-diagnostics/` виключено з Git.

При штатному виході після завершення Telegram записуються `session_status=finished`
і `ended_at`. Це підтвердження фінального знімка, не гарантія відсутності помилок
у сесії. Після SIGKILL/аварії лишається останній успішний періодичний знімок із
`session_status=running`; це не свідчить, що процес досі працює. Дані між останнім
успішним записом та аварією можуть бути втрачені. Позначка завершення в давніх
імпортованих знімках може бути відсутня. Під час ініціалізації до запуску heartbeat
в історії є початковий знімок; періодичні оновлення починаються разом із heartbeat.

У `config.py` визначені межі зберігання:

| Параметр | Типове значення |
| --- | ---: |
| `DIAGNOSTICS_HISTORY_DAYS` | 14 днів без оновлення архівного файла |
| `DIAGNOSTICS_HISTORY_MAX_SESSIONS` | 100 сесій |
| `DIAGNOSTICS_HISTORY_MAX_BYTES` | 50 МіБ загалом |

Очищення відбувається під час збереження. Старі файли видаляються раніше, якщо
досягнуто ліміту кількості або обсягу; поточний знімок сесії захищений. Розмір одного
знімка обмежено 2 000 000 байтів. Незавершені тимчасові файли після аварії
прибираються лише після години. Чужі файли й символічні посилання не видаляються.

Історію можна відкрити в локальній панелі: **Система → Історія сесій діагностики**.
Є вибір сесії, її метрики й завантаження JSON. Маршрути
`GET /api/diagnostics/history` та `GET /api/diagnostics/history/<session_id>`
потребують локальної авторизації; на публічному Telegram API їх немає.
Файл поточної сесії також оновлюється в списку, старі сесії лишаються доступними
до спрацювання меж зберігання. Для перевірки порівняйте дві сесії після планового
перезапуску: у попередньої мають лишитися її лічильники та часові метрики.

Історія починає накопичуватися після запуску оновленого коду. Втрачені раніше
нічні показники автоматично не відновлюються. Робоча SQLite не змінюється
механізмом архівування. Звичайні журнали застосунку можуть містити тексти ефіру
і залишаються приватними.

| Метрики | Значення |
| --- | --- |
| `telegram.*.attempts`, HTTP-коди | Спроби запитів, включно з повторами |
| `api_confirmed/api_rejected` | Прийняття або відмова Telegram, а не прочитання оператором |
| `delivery_uncertain` | Надсилання обірвалося; без відповіді можливі і втрата, і дубль |
| `queue_wait`, `queue_depth`, `queue_overflow` | Очікування, розмір та переповнення черги |
| `queue_discarded_off`, `notify_after_shutdown`, `shutdown_pending` | Явно спостережувані пропуски та незавершені надсилання |
| `ogg_conversion`, `conversion_failed`, `text_fallback`, `voice_exhausted` | Конвертація й резервний текст |
| `update_processing_error`, `update_quarantined`, `quarantine_write_failed` | Помилки команд і необхідність перевірки карантину |
| `duplicate_update_skipped` | Повторне вже підтверджене оновлення |
| `asr.whisper`, `asr.qwen`, `asr.correction_pipeline` | Тривалість етапів |
| `models.*`, `workers.*`, `audio.*` | Моделі, потоки, перезапуски й витіснення з аудіочерг |
| `asr.*_filtered`, `asr.low_rms`, `llm.rejected_*`, `llm.generation_error` | Причини відхилення або помилки |
| `receiver.suspensions`, `receiver.suspended` | Розриви приймання понад 60 с (сон Mac, закрита кришка, зупинка процесу) та їхня тривалість |
| `audio.stream_stalls` | Відкритий мікрофон 10 с не надсилав кадрів; потік перевідкрито |
| `telegram.alert_sent`, `telegram.alert_failed` | Службове повідомлення активним адміністраторам надіслано або спроби вичерпано |
| `asr.unhealthy`, `asr.health` | Розпізнавання зависло понад 3 хв або 5 помилок Whisper поспіль (`stuck`/`failing`/`ok`) |
| `telegram.recipients_unavailable` | Отримувачів не прочитано з БД: сповіщення пропущено, щоб не надіслати відключеним |
| `backup.created`, `backup.failed` | Щоденна автоматична копія бази створена або не вдалася (див. журнал) |
| `vad.short_discarded`, `vad.short_discarded_speech` | Фрагменти, коротші за `MIN_SPEECH_MS`, і тривалість мовлення в них, с |
| `asr.low_rms_level`, `asr.accepted_rms_level` | RMS відкинутих і прийнятих сегментів (поле `*_s` тут — рівень, не секунди) |

Затримки містять середнє й максимум за сесію та p95 останніх 128 вимірювань.
Long polling `getUpdates` близько 30 секунд є штатним очікуванням, а не затримкою
надсилання. Відмова Qwen не дорівнює помилці — консервативна перевірка зберігає
початковий варіант. Різниця кількості запитів і повідомлень може пояснюватися
особистим режимом OFF, зміною ролі чи режиму під час очікування в черзі,
командами бота, повторами та резервним текстом. Загального режиму немає;
`TELEGRAM_CHAT_ID` використовується лише для першої реєстрації адміністратора.
Якщо база прав недоступна, отримувачі не підміняються чатом із `.env`.

`TG_DIAG` у журналі містить операцію, знеособлений результат і час запиту.
Для сповіщень також є випадковий `notification`, порядковий номер `recipient`
(не Telegram ID), номер `attempt`, час у черзі `queue_wait_s`, розмір OGG
`audio_bytes` та округлена тривалість аудіо `audio_duration_s`.
Однаковий `notification` з різними `attempt` — повтор надсилання; різні
`notification` — окремі постановки в чергу, навіть коли тексти однакові.
ID пов’язує рядок «черга Telegram» з HTTP-спробами та резервним текстом,
не потрапляє до лічильників і не є ключем захисту від дублів.

`api_result=confirmed` означає HTTP 200 і `ok=true` від Telegram;
`rejected` — `ok=false`; `unverified` — підтвердження не отримано.
При `ReadTimeout` голосове могло вже надійти користувачу: наступна спроба
може створити дубль. Підтвердження резервного `sendMessage` не підтверджує
попередній `sendVoice`. Число спроб, тайм-аути та затримки повторів не змінено.

`connection_reset` визначається зі структури винятку без запису його тексту
в діагностичні метрики. Аналіз історичних журналів підтримує старі російські
та нові українські повідомлення.

## Затримка розпізнавання одного сегмента

Після перезапуску приймача нові дані з’являються у `diagnostics.json` →
`asr_latency`. Додаткові моделі чи робочі потоки не запускаються, пороги й
параметри якості не змінюються. Запис JSON залишається в наявному heartbeat,
приблизно раз на 30 секунд, а не в аудіоколбеку або після кожного сегмента.

`recent_segments` містить останні 128 оброблених сегментів. У кожному є лише
порядковий номер цієї сесії, часові мітки, тривалості, лічильники та стан;
PCM, розпізнаного тексту, позивних, Telegram ID та винятків там немає.

| Поле | Значення |
| --- | --- |
| `audio_end_unix_s` | Кінець останнього аудіокадру сегмента, включно з кінцевою тишею |
| `speech_end_unix_s` | Кінець останнього кадру, який WebRTC VAD позначив як мовлення |
| `enqueued_unix_s`, `processing_started_unix_s`, `text_ready_unix_s` | Передача в чергу, початок обробки, готовність підсумкового тексту |
| `capture_source` | `portaudio` — мітка ADC; `callback` — наближена мітка колбека; `legacy` — старий формат без міток захоплення |
| `audio_duration_s` | Довжина початкового PCM-сегмента, з preroll і кінцевою тишею |
| `speech_tail_s` | Від останнього речового кадру до кінця аудіосегмента |
| `capture_to_enqueue_s` | Від кінця аудіосегмента до передачі в чергу, з урахуванням буферизації захоплення та обробки кадрів |
| `vad_release_s` | Від кінця останнього речового кадру до передачі в чергу: попередні два інтервали разом |
| `queue_wait_s` | Очікування готового сегмента в черзі розпізнавання |
| `whisper_s`, `qwen_s`, `whisper_calls`, `qwen_calls` | Час і число викликів моделей саме для цього сегмента; без Qwen — нулі |
| `correction_s` | Словесні правила, Qwen і перевірки корекції разом; включає `qwen_s` |
| `notification_filter_s` | Перевірка локальних зразків звуків сповіщень |
| `processing_to_text_s` | Обробка сегмента до готовності тексту, без очікування черги та запису події |
| `total_latency_s` | Від кінця останнього речового кадру до готовності тексту |
| `segment_to_text_s` | Від передачі готового сегмента в чергу до готовності тексту |
| `rtf` | `processing_to_text_s / audio_duration_s`; це відношення, не секунди |
| `event_s`, `worker_busy_s`, `worker_rtf` | Подальша обробка події, весь час зайнятості обробника та його відношення до довжини аудіо |
| `queue_depth`, `segments_dropped` | Спостережені черга й загальне число витіснених сегментів на початку обробки |

Мітки календарного часу зберігаються в Unix-секундах; тривалості рахуються
монотонним годинником `perf_counter`, тому зміна системного часу їх не псує.
Час ADC першого зразка перераховується в кінець буфера за частотою дискретизації
й переноситься у відлік монотонного годинника через різницю часів PortAudio.
Якщо ці мітки недоступні, використовується час колбека. Межа мовлення визначена
VAD з точністю до кадру, а не незалежною ручною розміткою закінчення фрази.

```text
total_latency_s = vad_release_s + queue_wait_s + processing_to_text_s
vad_release_s = speech_tail_s + capture_to_enqueue_s
```

`ready` містить агрегати тільки готових текстів (включно з поверненням до тексту
Whisper після помилки корекції). Відкинуті за RMS, порожні, застарілі та помилкові
сегменти не занижують ці середні. `all_segments` окремо містить зайнятість
обробника для всіх оброблених сегментів. Для кожного показника є `count`,
`mean` і `max` за сесію, а `recent_p95` — точний p95 останніх 128 значень цього
показника. Вікно різних показників може відрізнятися через пропуски або відмови.
Поточний p95 не є p95 усієї багатогодинної сесії. Окремі p95 Whisper і Qwen
не можна додавати для отримання p95 повної затримки.

`audio.segments_queue` й `audio.segments_dropped` оновлюються також при передачі
та початку обробки сегмента. `asr.segment_queue_peak` зберігає максимум черги,
навіть якщо до знімка вона спорожніла. `asr.enqueued` / `asr.dequeued` рахують
передачі; `asr.queue_cleared` — штатне очищення черги при паузі/перевідкритті,
окремо від переповнення. `asr.outcome.*` розділяє причини завершення.
Старі `bytes` та `(generation, bytes)` залишаються сумісними; для них не
вигадуються відсутні мітки, а `asr.timing_missing` пояснює відсутність затримки.

Показати лише агрегати готовності тексту без приватного журналу:

```bash
python3 -c 'import json; d=json.load(open("diagnostics.json")); print(json.dumps(d.get("asr_latency", {}).get("ready", {}), indent=2))'
```

Порядок перевірки та попередній висновок: [ASR_LATENCY.md](ASR_LATENCY.md).

## Тривала перевірка

1. Перезапустіть служби через `start_radio345.py`, не запускаючи другий приймач.
2. Зберіть 24 години звичайного навантаження, локально архівуючи знімки метрик.
3. Перевірте затримки, черги, HTTP 429/5xx, обриви з’єднань, перезапуски й втрати кадрів.
4. Вручну зіставте кілька реальних повідомлень із Telegram: агрегати не доводять
   повноти доставки. Не надсилайте синтетичні повідомлення користувачам заради тесту.
5. Для оцінки Whisper потрібні аудіо й перевірені еталонні тексти; самі лічильники
   не дають WER або оцінки коротких позивних. Зміни фільтрів і повторів робіть
   після вимірювань та окремих тестів.

Telegram розділено на `services/telegram_common.py` (HTTP і метрики),
`telegram_outbox.py` (черга й голосові), `telegram_access.py` (доступ і режими)
та `telegram_updates.py` (long polling); `telegram.py` збирає їх у сервіс.

Автоматичні перевірки: `.venv/bin/python -m pytest -q -p no:cacheprovider` і
`node --test tests/miniapp.test.cjs`. Вони перевіряють транзакції, відновлення,
безпеку чисел і позивних та знеособлення діагностики на тимчасових даних,
але не вимірюють якість живої MLX-моделі.

## Локальний перегляд діагностики

`start_radio345.py --local-admin` запускає окрему панель на 127.0.0.1:8766.
Вхід — приватним локальним URL з `.radio345-local-admin/access-url.txt` (не публікувати).
Панель читає наявний `diagnostics.json`: середні й максимуми за запуск, p95 останніх
128 сегментів. Дані не стають публічними API-маршрутами й не містять текстів або аудіо.
Окремо показано кількість відомих копій Telegram, очікуваних правок і правок із
вичерпаними спробами. Лічильники `telegram.correction_edit_*` стосуються лише
оновлення тексту; механізм повторного надсилання голосових не змінений.

Права ролей і порядок ручної перевірки: [LOCAL_ADMIN.md](LOCAL_ADMIN.md).
