# 🩺 Діагностика

[← Вікі](README.md)

Для взаємодії SQLite-процесів без робочих даних:
`.venv/bin/python tools/check_sqlite_concurrency.py` — 4 процеси, синтетичні
пауза/hold, події, архівна розмітка й читання, перевірка обох індексів.
Регресії POSIX-блокувань: `tests/test_sqlite_file_locks.py`.

Перевірка панелі в справжньому браузері: `node tools/check_panel_ui.cjs`.
Потрібні `.venv`, Chrome (або шлях `CHROME_BIN`) і Node з WebSocket.
Тест піднімає окремий loopback API на випадковому порту з тимчасовою синтетичною
БД/аудіо й окремим профілем браузера; робочі служби не зупиняє. Перевіряє
вибірки, редактор/маркер, навчання, чернетки кодів і реальне збереження словника.
Знімки й шлях тимчасового каталогу залишаються для огляду після завершення.

Звичайні файлові журнали залишають назви етапів замість розпізнаного змісту;
текст лишається в живій консолі. Файли БД/журналів і відомі ротації отримують
приватні права під час відкриття. Старі тексти у вже створених журналах не стираються
заднім числом — зникають зі штатною ротацією або після окремого рішення власника.

На зупинці спочатку закривається захоплення, потім ASR отримує до 12 секунд на чергу,
і лише після цього закриваються Telegram та архів. `asr.shutdown_drained` підтверджує
завершення; `asr.shutdown_unfinished` рахує незавершені сегменти при перевищенні строку.
Пізній результат покинутого ASR не передається в події чи вже закритий архів.

## Перевірка без зупинки приймача

```bash
.venv/bin/python diagnose_radio345.py --verify-backup --network
```

| Частина | Що робить |
| --- | --- |
| без прапорців | SQLite лише на читання (цілісність, ключі, правила, heartbeat), розбір `radio*.log`, знімок метрик |
| `--verify-backup` | тимчасова копія бази → перевірка → видалення |
| `--network` | лише GET: локальний API (очікується 401), HTTPS API Mini App, Telegram `getMe` |

Не імпортує MLX, не відкриває мікрофон, не надсилає повідомлень, не змінює offset.
Звіт без текстів, аудіо, ID і токенів. Код виходу 1 — помилка бази, копії чи мережі.

## Метрики приймача

`diagnostics.json` (0600) — останній знімок, оновлюється разом із heartbeat
приблизно кожні 30 с. Кожна сесія ще й окремо: `.local-diagnostics/<початок>-<id>.json`
(14 днів / 100 сесій / 50 МіБ). Перегляд і завантаження — **Система → Історія
сесій діагностики**. Після аварії лишається останній знімок зі
`session_status=running` — це не означає, що процес живий.

Середні, максимуми й лічильники — за сесію; **p95 — за останні 128 сегментів**.

| Група | Що показує |
| --- | --- |
| `telegram.*` | спроби, HTTP-коди, `api_confirmed`/`rejected`, `delivery_uncertain`, черга, резервний текст |
| `asr.*`, `models.*`, `workers.*` | тривалість етапів, причини відсіву (`asr.outcome.*`), стан потоків |
| `audio.*`, `vad.*` | втрати кадрів і сегментів, зависання мікрофона, короткі фрагменти |
| `receiver.suspensions`, `receiver.suspended` | кількість/тривалість розривів циклу від 60 с, коли мікрофон до розриву був відкритий; це не доказ сну Mac |
| `receiver.loop_gaps`, `receiver.loop_gap` | усі довгі розриви циклу; суфікси `.active` / `.pause` / `.listening` / `.unavailable` відокремлюють активний потік, ручну паузу, прослуховування й недоступний мікрофон |
| `receiver.last_loop_gap_state`, `receiver.last_loop_gap_unix_s` | стан до останнього розриву й час його виявлення; тільки технічні дані |
| `asr.health` | `ok` / `stuck` (> 3 хв) / `failing` (5 помилок поспіль) |
| `backup.*`, `recordings.*` | автокопії, запис архіву |

`confirmed` — Telegram відповів `ok=true`, а не «оператор прочитав». При
тайм-ауті голосове могло дійти — повтор може дати дубль.
Розрив із закритим через паузу/прослуховування мікрофоном записується в діагностику,
але не створює Telegram-тривоги про втрату приймання. Пауза зі справним циклом
сама по собі не збільшує жоден лічильник розривів. Історичні сесії до цього
виправлення могли рахувати паузу як `receiver.suspensions`; їх не перераховують.

## Перевірка стабільності SQLite

Для відтворюваної перевірки SQLite окремо від робочого ефіру:

```bash
.venv/bin/python -m tools.check_sqlite_concurrency
.venv/bin/python -m tools.check_sqlite_concurrency --seconds 120 --interval .02
```

Інструмент завжди створює й прибирає тимчасові бази та синтетичні WAV,
не приймає шлях до робочих даних. Чотири процеси перевіряють ручну паузу/hold,
запис, розмітку й читання; додаткові потоки — heartbeat і паралельне читання.
Наприкінці JSON містить лічильники commit, exitcodes і результат integrity_check.
`--seconds` задає мінімальний час кожного процесу, `--interval` обмежує навантаження.
Це не перевірка MLX чи справжнього мікрофона й не заміна історії робочих сесій.

## Затримка одного сегмента

`diagnostics.json → asr_latency`: `ready` — агрегати готових текстів,
`recent_segments` — останні 128 сегментів (лише час, без тексту й аудіо).

```text
total_latency_s = vad_release_s + queue_wait_s + processing_to_text_s
vad_release_s   = speech_tail_s + capture_to_enqueue_s
```

| Поле | Значення |
| --- | --- |
| `speech_tail_s` | від останнього мовлення до кінця сегмента (тиша VAD) |
| `queue_wait_s` | очікування в черзі розпізнавання |
| `whisper_s`, `correction_s` | Whisper; правила й перевірки після нього |
| `processing_to_text_s` | обробка до готового тексту |
| `rtf` | обробка / довжина аудіо (відношення, не секунди) |
| `event_s` | подія й постановка сповіщення (не доставка) |

Порожня черга в знімку не доводить відсутності затримок — дивіться
`queue_wait_s`, пік черги й втрати за сесію. p95 Whisper і p95 корекції не
можна додавати.

```bash
python3 -c 'import json; print(json.dumps(json.load(open("diagnostics.json"))["asr_latency"]["ready"], indent=2))'
```

## Тривала перевірка

Зберіть 24 год звичайного ефіру, перевірте затримки, черги, HTTP 429/5xx,
обриви й втрати, вручну зіставте кілька повідомлень у Telegram. Якість Whisper
лічильники не показують — для неї потрібні [еталони](archive.md) і
[лабораторія](lab.md).

## Затримки локальної панелі

Метрики Whisper не вимірюють швидкість редактора. Для архіву окремо дивіться
вкладку Network у засобах розробника браузера: `/api/recordings`,
`/api/recordings/summary`, `/api/text-check` і `PUT …/review`.
Розрізняйте очікування перевірки тексту до PUT, сам запис еталона й
перемальовування після відповіді. Запис еталона, пов'язаного з подією, також
синхронізує подію та ставить оновлення Telegram у чергу; HTTP-відповідь не
підтверджує доставку в Telegram.

20.11.2026 профіль на тимчасовій копії індексу (1977 еталонів) виявив у
`RecordingStore.summary()` 3733 обчислення початку доби й непотрібний розрахунок
`number_match`. Після усунення зайвого медіана п'яти викликів змінилася
669 → 87 мс, відповідь збіглася повністю. Це час методу на копії бази,
а не вимір повного завантаження сторінки під навантаженням приймача.
Детальні картки зберегли перевірку чисел; правила розпізнавання не змінювались.

Перевірки однакового тексту, що виконуються одночасно в одній картці,
використовують один запит. Завершені відповіді не кешуються: після зміни
словника наступна перевірка читає актуальні дані. Під час очікування blur-правки
повторне збереження блокується, а кнопка одразу показує «Зберігаю…».
