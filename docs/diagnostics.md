## Перевірка без зупинки приймача

```bash
.venv/bin/python diagnose_radio345.py --verify-backup --network
```

| Частина | Що робить |
| --- | --- |
| без прапорців | SQLite лише на читання (цілісність, ключі, правила, heartbeat), розбір `radio*.log`, знімок метрик |
| `--verify-backup` | тимчасова копія бази → перевірка → видалення |
| `--network` | лише GET: локальний API (очікується 401), HTTPS API Mini App, Telegram `getMe` |

Не імпортує MLX, не відкриває мікрофон, не надсилає повідомлень, не змінює offset.
Звіт без текстів, аудіо, ID і токенів. Код виходу 1 — помилка бази, копії чи мережі.

## Метрики приймача

`diagnostics.json` (0600) — останній знімок, оновлюється разом із heartbeat
приблизно кожні 30 с. Кожна сесія ще й окремо: `.local-diagnostics/<початок>-<id>.json`
(14 днів / 100 сесій / 50 МіБ). Перегляд і завантаження — **Система → Історія
сесій діагностики**. Після аварії лишається останній знімок зі
`session_status=running` — це не означає, що процес живий.

Середні, максимуми й лічильники — за сесію; **p95 — за останні 128 сегментів**.

| Група | Що показує |
| --- | --- |
| `telegram.*` | спроби, HTTP-коди, `api_confirmed`/`rejected`, `delivery_uncertain`, черга, резервний текст |
| `asr.*`, `models.*`, `workers.*` | тривалість етапів, причини відсіву (`asr.outcome.*`), стан потоків |
| `audio.*`, `vad.*` | втрати кадрів і сегментів, зависання мікрофона, короткі фрагменти |
| `receiver.suspensions` | розриви приймання понад 60 с (сон Mac) |
| `asr.health` | `ok` / `stuck` (> 3 хв) / `failing` (5 помилок поспіль) |
| `backup.*`, `recordings.*` | автокопії, запис архіву |

`confirmed` — Telegram відповів `ok=true`, а не «оператор прочитав». При
тайм-ауті голосове могло дійти — повтор може дати дубль.

## Затримка одного сегмента

`diagnostics.json → asr_latency`: `ready` — агрегати готових текстів,
`recent_segments` — останні 128 сегментів (лише час, без тексту й аудіо).

```text
total_latency_s = vad_release_s + queue_wait_s + processing_to_text_s
vad_release_s   = speech_tail_s + capture_to_enqueue_s
```

| Поле | Значення |
| --- | --- |
| `speech_tail_s` | від останнього мовлення до кінця сегмента (тиша VAD) |
| `queue_wait_s` | очікування в черзі розпізнавання |
| `whisper_s`, `correction_s` | Whisper; правила й перевірки після нього |
| `processing_to_text_s` | обробка до готового тексту |
| `rtf` | обробка / довжина аудіо (відношення, не секунди) |
| `event_s` | подія й постановка сповіщення (не доставка) |

Порожня черга в знімку не доводить відсутності затримок — дивіться
`queue_wait_s`, пік черги й втрати за сесію. p95 Whisper і p95 корекції не
можна додавати.

```bash
python3 -c 'import json; print(json.dumps(json.load(open("diagnostics.json"))["asr_latency"]["ready"], indent=2))'
```

## Тривала перевірка

Зберіть 24 год звичайного ефіру, перевірте затримки, черги, HTTP 429/5xx,
обриви й втрати, вручну зіставте кілька повідомлень у Telegram. Якість Whisper
лічильники не показують — для неї потрібні [еталони](archive.md) і
[лабораторія](lab.md).
