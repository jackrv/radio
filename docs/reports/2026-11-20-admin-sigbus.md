Нижче збережено первинну хронологію та межі початкового діагнозу.

20.11.2026, перевірено commit `3f7f8b8b30ae3aa2ea1e67b54824d3edede2de65`
із незакоміченими змінами. Аналіз лише на читання; службу не перезапускали,
робочу БД/WAL/SHM не змінювали. Це робоча панель, не синтетичний тест.

## Виміряні факти

- О **23:12:35 +0200** завершився процес локальної панелі. Контролер записав
  `SIGBUS (10)`, лаунчер — код 246 і зберіг роботу приймача.
- Звіт macOS `Python-2026-11-20-231236.ips`: `EXC_BAD_ACCESS / SIGBUS`,
  `FS pagein error: 22 Invalid argument`. Стек: `_platform_memmove` →
  `walIndexReadHdr` → `walTryBeginRead` → `sqlite3PagerSharedLock` →
  `sqlite3_step` → Python sqlite3. Fault address міститься у mapped file 32 KiB.
- Це відповідає читанню WAL-індексу; конкретний шлях mapped file у звіті не вказаний.
  Тому не доведено, чи це `events.db`, чи індекс аудіоархіву.
- Читання списку процесів і listener порту: приймач, API Mini App, ngrok і лаунчер
  працюють; локальної панелі/слухача TCP 8766 немає. Журнал приймача продовжує оновлюватися.
- У журналі перед падінням були кілька перерв приймання на 1–5 хв із повідомленням
  «сон Mac або зупинка процесу». Це часовий контекст, не доведений причинний зв'язок.
- Ранішній робочий збій о **15:04:40** також мав SIGBUS і `walIndexReadHdr`,
  але тоді впав приймач. Окремий тестовий збій MLX о 15:43 був SIGABRT і не є цим інцидентом.
- Метадані поточних основних БД не містили прапорця `dataless`. Це не виключає
  попереднього файлового збою чи інших властивостей файлової системи.

## Межі й наступні кроки

Першопричину не встановлено: стек не доводить пошкодження БД, дефект конкретної
Python-функції або проблему хмари/диска/сну. Зв'язок із останніми UI-правками не доведений.
Оскільки SIGBUS відбувається всередині native sqlite3, звичайний Python try/except
не є виправленням такого завершення.

Для дослідження потрібні збережений crash report, стан файлової системи й версія
SQLite; перевірка цілісності на резервній копії та аналіз життєвого циклу WAL/SHM.
Не видаляти WAL/SHM і не перемикати режим журналу в живій системі наосліп.
Повний перезапуск лаунчера перерве приймач і потребує явного рішення власника.
Ручний запуск лише панелі в окремому терміналі можливий штатним
`.venv/bin/python -m api.local_dashboard --open`, але не усуває першопричини.

Додаткова перевірка: робоче середовище Python 3.12.16 / SQLite 3.54.1;
crash image також `libsqlite3.3.54.1.dylib`. Проєкт — звичайний шлях у Documents,
прапорця dataless у перевірених каталогів не видно. На Data-volume близько 14 GiB
вільно; це не доказ ENOSPC. Стан iCloud/помилки APFS цим не встановлено.
[SQLite WAL format](https://www.sqlite.org/walformat.html) підтверджує, що WAL-index
зазвичай є mmap файлу `-shm`; конкретна БД та причина помилки page-in лишаються невідомими.

## Уточнення власника й журнал живлення

Власник повідомив, що перед збоєм натиснув кнопку зупинки приймача у верхній
частині панелі; кришку не закривав, помічав лише вимкнення екрана.
Це свідчення не слід підміняти припущенням про закриту кришку.

Незалежна перевірка `pmset -g log` за 20.11.2026 зафіксувала:

- **23:08:58**: `Entering Sleep state due to 'Maintenance Sleep'`, 76 секунд.
- **23:10:14**: `Wake from Deep Idle ... UserActivity Assertion`.
- **23:10:15**: `Display is turned on`.
- О **23:10:14** застосунок повідомив про приблизно хвилинну перерву.

Отже, принаймні цей проміжок був системним сном/deep idle, а не лише погашеним
екраном; він не доводить закриття кришки. Падіння SQLite сталося пізніше, о 23:12:35,
тому сон підтверджено, але причинний зв'язок із SIGBUS **ще не доведений**.

У коді знайдено окреме обмеження повідомлень: supervisor визначає часовий розрив
циклу за wall/monotonic, не читає macOS sleep-events, і викликає `on_suspension`
навіть під час навмисної паузи. Журнал містить паузу з закриттям мікрофона о 22:22:16.
Для встановлення наслідків конкретного натискання перед SIGBUS потрібна його точна
операція; записи повної зупинки приймача через лаунчер безпосередньо перед падінням
не знайдені. У цьому етапі код/налаштування не змінювалися.

## Перетин паузи оператора й прослуховування архіву

Власник уточнив: збій під час розмітки/відтворення архіву при глобально вимкненому
прослуховуванні. Перевірено `reception_request`, `set_listening_hold`, browser hold
та `supervisor.transition`. Глобальна часова пауза й коротке утримання відтворення
мають різні таблиці; спочатку перевіряється глобальна пауза. Відпускання hold не
знімає її, а API hold сам не запускає процес приймача, якщо його зупинено лаунчером.

**19 адресних тестів passed** (`test_listening_hold`, `test_receiver_control`), включно
з новими регресіями одночасного оновлення hold/читання глобальної паузи й переходу
на активне утримання після закінчення глобальної паузи. Бази лише тимчасові.
Логічний конфлікт, який би самовільно скасовував глобальну паузу, не відтворено.

Відтворення все одно викликає записи hold до SQLite, зокрема heartbeat раз на 4 с;
розмітка також звертається до БД. Отже, це можливий шлях SQL-запиту, що проявив
низькорівневу проблему, але native SIGBUS самим перетином двох прапорців не пояснений.
Тести не відтворювали системний сон/FS page-in і не спростовують збій живої системи.
Продукційний код у цій перевірці не змінювався.
