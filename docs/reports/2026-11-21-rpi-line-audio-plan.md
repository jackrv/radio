## Перевірений поточний стан

- `config.py`: `MODEL_REPO=mlx-community/whisper-large-v3-mlx`, `USE_LLM=False`,
  mono/16 kHz у захопленні. Найновіша архівна settings теж full large-v3,
  Qwen вимкнено. Старі turbo/Qwen-таймінги не є вимірами цієї конфігурації.
- `core/recognition.py` безпосередньо використовує mlx_whisper; локальне
  джерело аудіо — PortAudio RawInputStream у supervisor. Окремого мережевого
  джерела Pi зараз немає, потрібен адаптер входу й протокол доставки.
- Readonly-запит індексу: **1317** записів speech із непорожнім reference
  й duration 0–30 с, **~2,19 год**. Це число на момент перевірки, не сталий ліміт.
  `services/training_set.py` уже вміє вивантажити WAV/reference й часовий test-split;
  вивантаження/навчання цього разу не виконувалося.

## Що може дати лінійний звук

Очікується усунення кімнатних звуків, відстані до динаміка й акустичної луни,
стабільніший рівень за правильного узгодження. Це може зменшити хибні VAD
і галюцинації та дозволити меншу модель — **не виміряно**. Шуми радіоканалу,
обрізання початку передачі, перевантаження, незвичні назви/цифри лишаються
окремими причинами помилок. Чистіший сигнал не робить full large дешевим
автоматично на кожній однаковій тривалості аудіо.

До підключення звірити справжній line-out/line-in за документацією конкретних
пристроїв. Вихід динаміка й мікрофонний вхід не вважати еквівалентними line.
Калібрування рівня/RMS для нового тракту — окрема перевірка, не сліпе копіювання.

## Варіанти

1. Спочатку рація → USB-аудіокарта → Mac. Зберігається чинний ASR; можна
   ізолювати вплив нового джерела без змішування з ефектом меншої моделі.
2. Pi захоплює PCM, буферизує та передає на Mac. На першому етапі VAD і ASR
   лишити на Mac, щоб рання нарізка Pi не приховала короткі слова. Надалі
   локальний VAD можливий після тестів початку/кінця й preroll.
3. Повністю автономна Pi потребує Linux/ARM backend та експерименту з меншою
   мультимовною моделлю. Не обіцяти темп full large-v3 на Pi. whisper.cpp
   документує Raspberry Pi, CPU й квантування; кандидати base/small мають
   перевірятися на українській радіомові, не на англійському прикладі `.en`.

В Apple-ускорення Metal немає прямого еквівалента на Pi. При цьому не писати,
що MLX взагалі існує лише для macOS: актуальна документація має Linux CPU/CUDA.
Це не доводить придатність саме pinned mlx-whisper/ARM Pi для цього конвеєра.
Сумісність runtime, вміщення у RAM і швидкість — три різні перевірки.

## Межа захоплення й ASR

Пропозиція: Pi → автентифікований транспорт → Mac зі стійким прийманням,
єдиним конвеєром, подіями та Telegram. Сесія/порядковий номер сегмента,
timestamp, reconnect, контроль переповнення, обмеження диска й повтор
без дублювання. Pi не видаляє ще не підтверджене аудіо; ACK має означати
стійке збереження завдання/результату, а не лише запис у TCP-сокет.
Сон/недоступність Mac тоді накопичує чергу, але не дає негайного ASR.
Не під'єднувати два вузли до спільної SQLite на SMB/NFS; обмін через API,
власник робочої БД один. Протоколу/реалізації тут поки немає.

PCM16 mono 16 kHz: 16000×2 = **32000 байт/с**, 256 кбіт/с без overhead,
115,2 MB/год безперервного звуку. Це арифметика формату проєкту. Для LAN
можна спершу лишити PCM, не додавати втратне стиснення перед порівнянням ASR.

## Що переносити

- Словники/налаштування/безпечні словесні правила — корисні й для іншого ASR.
  Його профіль помилок відрізнятиметься: перевіряти правила на нових еталонах.
- WAV + еталони потрібні для незалежного порівняння та можливого донавчання.
  Поточна розмітка не змінювала ваги Whisper автоматично. Старі кімнатні
  записи корисні, але не заміняють приклади нового line-тракту.
- Повний історичний аудіокорпус не потрібний для звичайного inference й не
  повинен дублюватися на Pi, якщо ASR/розмітка лишаються на Mac.
- Локальний буфер Pi для недоступної мережі/Mac — окреме тимчасове сховище.
  Не видаляти ще не оброблене за правилом low_rms 1 год: статус розпізнавання
  ще невідомий, це аналог захищеного deferred. Строк/ліміт і дії при переповненні
  потребують окремого рішення власника.

## План вимірювання до вибору автономної Pi

Зібрати 50–100 нових line-еталонів із номерами/позивними, короткими відповідями,
слабкими передачами й негативними прикладами. Поточний full large на Mac — база.
На тих самих фразах перевірити менші multilingual моделі за «без правок»,
цифрами/позивними, пропущеним мовленням і хибним текстом на тиші. Потім на Pi
виміряти час, RTF, p95 затримки й ріст черги під щільним потоком; тиша між
репліками може приховати нестачу продуктивності. Не переносити швидкість Mac
чи опублікованої чужої англійської демонстрації на український ефір Pi.

## Уточнення: що означає навчати ваги Whisper

Поточна правка еталона зберігає перевірений текст і кандидати словесних правил
SQLite. Вона не запускає optimizer і не змінює checkpoint Whisper. Справжнє
дообучення використовує **WAV + точний reference**, обчислює помилку моделі
й оновлює ваги або адаптер. Це може поліпшити первинний текст, але ефект
на нашому корпусі поки не виміряно.

У проєкті є підготовка/експорт корпусу, але немає перевіреного тренувального
конвеєра Whisper чи його ввімкнення в живий приймач. README mlx-whisper
описує inference і conversion; наявність LoRA для mlx-lm не означає готового
Whisper-тренера. Загальний офіційний маршрут існує через
[Transformers fine-tuning Whisper](https://huggingface.co/blog/fine-tune-whisper).
[PEFT](https://huggingface.co/docs/transformers/peft) зменшує кількість навчених
параметрів; підтримку конкретного Whisper/runtime/Apple MPS ще треба перевірити.
CUDA/4-bit рецепти не переносити на Mac без перевірки сумісності.

~2,19 год — підстава почати **пілот**, не гарантія виграшу й не магічний поріг.
Позначки 2/5 год у training_set.py — орієнтири обсягу, не доказ достатності.
Перед тренуванням: перевірка аудіо/еталонів і явний train/validation/test
за часовими блоками без витоку сусідніх передач. Збережений test не використовувати
для вибору правил чи checkpoint. Новий line-звук додати й перевіряти окремо.

Повне fine-tuning large-v3 на 16 GB не пропонується як простий робочий варіант:
потрібна пам'ять для градієнтів/optimizer/активацій понад inference. Придатність
адаптерів або меншого multilingual Whisper на Mac ще не заміряна. Для мети
автономної Pi доцільний кандидат меншого розміру; дообучення великої моделі
саме по собі не робить її меншою чи швидшою.

Пропонований етап: аудит набору → пілот окремого checkpoint → порівняння з
базовим на спільному відкладеному test за «без правок», номерами/позивними,
пропусками й хибним текстом на негативних прикладах → лише потім рішення
про застосування. Навчання не запускалося, приймач не зупинявся,
приватні WAV/тексти нікуди не передавалися.

## Уточнення оцінки часу першого пілоту

Планова оцінка, **не виміряний benchmark Mac**: приблизно 1–2 дні до першого
незалежного порівняння за умови працездатного локального тренера. Аудит/спліт
і сумісність/пам'ять — кілька годин роботи (орієнтир 2–6 год), навчальний
запуск попередньо планувати в окреме нічне вікно, оцінку — ще 1–2 год.
Несумісність backend або нестача пам'яті збільшить цей строк; повний large-v3
на 16 GB не є погодженим чи підтвердженим варіантом.

До повного запуску потрібен короткий тест 50–100 кроків: перевірка пам'яті,
seconds/step і часу evaluation. За ним оцінюється весь обраний бюджет кроків
плюс валідація/конвертація; обсяг аудіо не дорівнює часу навчання. Тест теж
змінює пробні ваги, тому лише окремий checkpoint і погоджене вікно без приймача.
Аудит/підготовка даних можуть виконуватися без зупинки приймання.

Для масштабу [приклад Hugging Face](https://huggingface.co/blog/fine-tune-whisper)
оцінює свій запуск small на GPU у 5–10 год (8 год Common Voice, 5000 кроків).
Це не оцінка нашої 2,19-годинної вибірки, M4 чи адаптерів. Тренер/залежності
не встановлювали, замір/навчання не запускали; строк «за ніч» не гарантовано.

## Уточнення: мікромодель для першого експерименту

Власник запропонував спробувати мікромодель. Рекомендація для перевірки —
**готовий multilingual Whisper tiny (39 M параметрів)** з дообученням на наших
парах, не модель з нуля. Base (74 M) — близький більший кандидат, якщо tiny
занадто сильно втрачає цифри/позивні. Для порівняння large — 1550 M:
~40-кратна різниця числа параметрів не є виміром прискорення чи точності.
[Офіційні розміри](https://github.com/openai/whisper#available-models-and-languages),
[картка multilingual tiny](https://huggingface.co/openai/whisper-tiny).

Окремий компактний детектор команд вирішує вужчу задачу й не замінює повний
текст вільного ефіру. Йому потрібні класи «інше/не впевнений/немає мовлення»,
а не примусовий вибір найближчої дозволеної команди/числа. Для такого детектора
ще немає окремої перевіреної вибірки класів. Vosk має українські nano/small
варіанти ([список виробника](https://alphacephei.com/vosk/models)); вказані там
73M/133M — обсяг завантаження, **не кількість параметрів**. Цей альтернативний
backend не встановлювали й під нашу задачу не оцінювали.

План ASR-пілоту: звичайна tiny, донавчена tiny та чинна large на спільному
відкладеному test; однакові словесні правила, також окремо сирий текст ASR.
Головне — «без правок», точні числа/позивні, пропуски та хибний текст на
немовленні; швидкість автономного виконання вимірюється саме на Pi.
Менший trainable checkpoint робить пілот доступнішим для Mac 16 GB, але
не знімає час аудиту/сумісності; години й реальну пам'ять уточнює тест
50–100 кроків. Жодного заміру, навчання чи зупинки приймача не виконували.
