## Цілісність робочих даних

Двічі створено приватні узгоджені snapshots через SQLite backup API: джерела
відкривалися `mode=ro`, без стороннього open/close DB/WAL/SHM. На кожній парі
копій `events.db` і `index.sqlite3` повний `PRAGMA integrity_check = ok`.
Перша перевірка — 16:05, завершальна — 19:09. Робочі рядки не змінювали,
WAL/SHM і `.radio345.lock` не видаляли. Snapshots у `.local-backups/`, технічні
агрегати — `.local-experiments/sqlite-stability-2026-11-21/`; приватний вміст
не потрібний для розуміння наведеного висновку й не публікується.

## Синтетичні перевірки

- Chrome `tools/check_panel_ui.cjs`: справжні зміни slider/API, відтворення
  синтетичного WAV, hold/release, збереження розмітки, явне resume. Глобальна
  пауза зберігається після play/pause і review. Окремий FastAPI й тимчасові
  SQLite, Chrome має `--mute-audio`; тестовий звук не потрапляє в живий мікрофон.
  Це справжній браузерний frontend/API-прохід; апаратного приймача у fixture немає.
- Розширено `tools/check_sqlite_concurrency.py`: тривалість/мінімум циклів/пауза,
  4 spawn-процеси, додаткові потоки heartbeat і читання в тих самих процесах.
  Нова послідовність control перевіряє pause → hold → release hold → resume.
  Один загальний timeout, очистка власних дочірніх процесів навіть при помилці.
  Робочий шлях інструмент навмисно не приймає.
- Прогін **120,182 с**: control 4226 циклів, receiver 4179, review 4344,
  read 2667; додаткові з'єднання 4807/4873. У базі рівно **4179 подій,
  4344 правки, 4180 WAV/архівних записів** (включно з початковим).
  Обидва integrity_check — ok, усі 4 exitcodes — 0. Це не навантаження MLX.
- Нові регресії перевіряють завершення stress і cleanup після timeout;
  SIGKILL власного тестового writer: незавершений INSERT відкинуто, новий writer
  успішно commit, база ціла. Чинні POSIX lock-проби також пройшли.

## Додатково знайдено й виправлено

У `services/archive_backup.py`, `services/archive_learning.py` та
`tools/asr_lab.py` SQLite connection context manager завершував транзакцію,
але не закривав source/target. У копіюванні архіву файл target далі читався
для SHA-256 при ще відкритому SQLite connection. Додано явний `closing`;
джерела й копії закриті до наступних операцій і при помилці backup.

Шість регресій (три шляхи × успіх/штучна помилка) перевіряють явне close
та відсутність прямого читання ще відкритої копії. Зв'язок цих додаткових
знахідок із минулим робочим SIGBUS **не встановлено**: вони працюють із копіями,
а первинний доведений дефект був у permission-helper живої бази.
