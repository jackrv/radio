# Разове очищення повідомлень Telegram

21.11.2026. HEAD `dbf832f69dfb4d6377efca5c78c24e3e322fc3a1`, main, із
незакоміченими попередніми змінами. Це окрема явно погоджена зовнішня операція,
не реалізація нової постійної команди. Commit/push і перезапуск не виконувалися.

## Доручення й межі

Власник доручив ботові видалити всі доступні повідомлення Telegram.
Первинний набір — 1236 унікальних chat/message адрес із наявних таблиць
telegram_deliveries, legacy media та службових карток; два особисті чати.
Службових карток з окремими адресами на початку не було, legacy додаткових
адрес не дав. Telegram не надає звичайному Bot API методу повного читання
історії, тому цей набір не вважали повним переліком усіх надісланих повідомлень.

Додаткове перебирання 307 пропущених ID автоматична перевірка відхилила:
вони могли бути вхідними або нерелевантними повідомленнями. Блок не обходили.
Після завершення первинного списку власнику пояснено ризик; він **окремо
дозволив будь-які повідомлення, включно з вхідними, у цих діапазонах обох чатів**.
Повторний запуск отримав дозвіл й обробив рівно 307 ID з незмінного початкового
snapshot, без розширення на нові чати чи подальші діапазони.

## Виконання й результат

Операція використовувала офіційний deleteMessages (пакети до 100), HTTP-обгортку
проєкту, розділення пакета при відмові, bounded retry для мережі та retry_after
при 429. Бот не надсилав sendMessage й не запускав паралельний getUpdates,
щоб не заважати чинному polling. Токен із локального середовища не виводився.

| Набір | Спробовано ID | Telegram підтвердив обробку | Telegram відмовив |
| --- | --- | --- | --- |
| Збережені адреси | 1236 | 843 | 393 |
| Окремо погоджені пропуски | 307 | 307 | 0 |
| Разом | **1543** | **1150** | **393** |

Підтвердження deleteMessages означає: придатне повідомлення видалено або
за цим ID воно вже було відсутнє. API пропускає not-found й не повертає
кількість реально вилучених повідомлень. **Не називати 1150 числом нових видалень.**
393 одиничні відмови класифіковані за повідомленням Telegram про неможливість
видалення. Загальне правило deleteMessage — менше 48 год; точний вік кожного
legacy-повідомлення без sent_at не відновлювали. Отже, не стверджуємо, що
причина кожної відмови доведена лише часом. Невирішених мережевих/серверних
помилок у кінцевому результаті немає.

## Локальний стан і приватність

До запису metadata створено перевірені SQLite snapshots у `.local-backups/`.
Після підтвердження API відповідні доставки позначені unavailable;
media-фраза позначена deleted лише коли не лишилося доступних копій.
Перевірка відомих успішних адрес підтвердила узгодженість unavailable.
Відмову API не видавали за успішне видалення.

Архів, еталони, події, словники, правила/голоси та налаштування користувачів
ця операція не видаляла й не переписувала. Нові повідомлення після фіксації
набору можуть надходити: режими розсилки не змінювалися. Результати з приватними
адресами й одноразові скрипти — тільки в ігнорованій
`.local-experiments/telegram-cleanup-2026-11-21/`, без коміту.

Перевірка цього етапу — відповіді справжнього Telegram й відповідна metadata,
не синтетичні тести. Код програми не змінено, повторний повний pytest не запускався;
`git diff --check` пройшов. Опис не замінює повну історію чату, якої API не віддав.

Первинне джерело: [Telegram deleteMessage / deleteMessages](https://core.telegram.org/bots/api#deletemessages),
перевірено 21.11.2026. Довільні інші діапазони в майбутньому потребують нового
явного доручення; дозвіл цієї операції не є постійним автоприбиранням чатів.
