помилки не зберігається, тому конкретну історичну причину лічильник не пояснює.

У «Система → Telegram» додано дві явні дії:

- **Повторити невдалі оновлення** повертає лише вичерпані актуальні правки у фонову
  чергу; потрібен працюючий бот. Запит панелі сам до Telegram не звертається.
- **Пропустити ці оновлення** після підтвердження зберігає `skipped_revision`,
  не підробляє `applied_revision` і не видаляє виправлений текст/навчання/доставки.
  Старий підпис може залишитися; нова правка підвищує revision і синхронізується знову.

Операції атомарні, лише для адміністратора (`settings.write`), із локальною
сесією/Origin. Не зачіпають майбутні помилки. Запитане видалення копії не враховується
як невдала правка. UI оновлює стан одразу, без ручного перезавантаження.

Міграція additive: `skipped_revision INTEGER NOT NULL DEFAULT 0`. Старі задачі не
змінюються до вибору оператора. Не замінювати API ручним UPDATE живої бази.

**1335 Python / 135 Node passed**, `git diff --check` пройшов. Регресії:
повтор/пропуск, ідемпотентність, нова правка після пропуску, збереження непідтвердженої
ревізії, відмова editor/viewer, Origin і допустимі дії. Браузерний smoke-тест на
тимчасових даних перевірив пропуск, API-стан і зникнення кнопок помилки в UI.
Telegram API та живі доставки під час перевірки не змінювалися.

Для нових серверних маршрутів/міграції потрібен перезапуск служб. Потім оператор
сам обирає повтор чи пропуск — агент не скидав живі помилки.
