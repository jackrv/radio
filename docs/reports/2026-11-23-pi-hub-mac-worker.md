# Архітектура: Pi — дім системи, Mac — вузол розшифровки

[← Звіти](README.md) · [Ідеї](../ideas.md) · [Raspberry Pi](../raspberry-pi.md)

Дата: 23.11.2026, на базі `ab8f899`; дерево мало сторонні незакомічені зміни. Це рішення
власника й огляд коду; реалізація та перевірки — в «Етапах» нижче. Рядки «факт» перевірено в коді,
«план» — ще ні.

## Рішення власника

- **Pi (завжди ввімкнена):** прослуховування ефіру, VAD, «наживо», PTT, `events.db`, архів, адмінпанель.
- **Mac:** лише вузол розшифровки (Whisper/MLX), без бази.
- Telegram, API для Mini App і застосунків ідуть за базою на Pi (наслідок: SQLite не відкривають по мережі).
- Один репозиторій; кожен пристрій отримує свій набір через `git sparse-checkout` і маніфест.

## Критерій приймання

| Подія | Очікування |
| --- | --- |
| Pi + телефон, без Mac | «наживо» і PTT працюють |
| Увімкнено Mac | розшифровка стартує без перезапуску Pi |
| Відкрито/закрито панель | ефір не змінюється |
| Закрито кришку Mac | працює все, крім нових текстів; фрази накопичуються на Pi |
| Відкрито кришку | накопичене розпізнано без дублів |
| Вимкнулась Pi | застосунок не падає, показує кеш і перепідключається |
| Pi завантажилась | служби піднялись, збережені фрази на місці |

## Факти з коду

- `Transcriber` отримує `recognizer` ззовні й використовує `prompt`, `transcribe(audio, prompt)`,
  `extract_text`, `warmup`, `unload`. Отже заміною `WhisperRecognizer` на мережевий клієнт
  фільтри, словники, позивні, події й Telegram лишаються на Pi без зміни логіки.
- `core.recognition` імпортує `mlx_whisper` на рівні модуля; `core.transcriber` бере звідти `is_looped`,
  а `transcriber_factory` — `WhisperRecognizer`. На Pi це не завантажиться: імпорт MLX треба відокремити.
- Режим «лише запис» уже пише фрази в архів як `deferred`, а потім розпізнає найстаріші у вільну хвилину.
  Такі записи **не створюють подій і Telegram**.
- Збій Whisper посеред фрази дає `whisper_error`, а не `deferred`: для мережевого клієнта це втрата тексту.
- Серед 96 модулів, досяжних з `api.local_dashboard`, немає імпорту MLX, sounddevice, webrtcvad.
  Панель розрахована на 127.0.0.1. `lab_queue` і `panel_jobs` запускають процеси локально.
- microSD на Pi 8 ГБ, вільно було ~3,4 ГБ (22.11). Архів 951 МБ, `.venv` на Mac 1,5 ГБ (з MLX).

## План

1. **Відокремити MLX:** `is_looped`, `extract_text` — у модуль без MLX; розпізнавач обирає фабрика.
2. **Вузол Mac:** HTTP-служба лише в Tailscale: звук, підказка, версія контракту → результат Whisper.
   Без бази; один запит за раз; model slot лишається на Mac. Pi звертається до Mac.
3. **Клієнт на Pi:** тайм-аути й health; «Mac недоступний» → `deferred`, а не `whisper_error`.
   Лабораторія зайняла модель → та сама відповідь «зайнято».
4. **Порівняння:** локально й через вузол на однакових записах тексти мають збігатися.
5. **Панель на Pi** з копією БД: замір пам'яті й CPU, вхід через Tailscale і `LoginName`, без Funnel.
6. **Перенесення** БД, архіву, бота, API одним перемиканням: backup і шлях відкату. Pi — єдиний власник БД;
   стару копію на Mac не запускати (подвійний бот і події).
7. **Лабораторія:** виконавець на Mac, копія архіву лише для читання.

Служби systemd окремі: ефір/PTT, розпізнавання з подіями, панель. Падіння панелі чи аналізу не
має зупиняти ефір. Наразі `radio.py` тримає ефір і розпізнавання в одному процесі.

## Ризики й обмеження

- Pi стає єдиною точкою відмови й зберігання: потрібні SSD замість 8 ГБ microSD і щоденний backup на Mac.
- PTT: апаратний обмежувач часу передачі; програмне відпускання не захищає від зависання ядра.
- USB-карта, line-звук, PTT на Pi, навантаження панелі й бота на Pi — не виміряно.
- Не вирішено: чи доганяти пропущене повідомленнями в Telegram (нині — лише архів).
- Не перевірено: чи може черга архіву (`submit`, `prune`) втратити `deferred` при довгій паузі Mac.

## Етап 3: справжній Whisper через вузол (23.11.2026)

Приймач зупинено власником; 40 останніх записів з еталоном, 393 с; звук на Pi лише в `/dev/shm`, видалено.

- Pi → Mac, large-v3: 40/40 відповідей, 0 помилок, у середньому 3,02 с (локально 2,92 с), максимум 11,4 с.
- Підготовлений звук на Pi і Mac побітово однаковий: 40/40. **Temperature 0: прямо = HTTP 40/40.**
- Зі звичайними температурами (0 / 0,2 / 0,4) тексти збіглись у 30/40; у пізніших прогонах усі розбіжності —

- Розбіжність виникає й без мережі та Pi. Чи змінюється якість, не виміряно: потрібен WER/«без правок» до еталона.
