# Ідея: один репозиторій, спільний код, окремі процеси

[← Звіти](README.md) · [Pi — дім системи](2026-11-23-pi-hub-mac-worker.md)

Дата: 23.11.2026. Пропозиція за побажаннями власника, схвалено `shared/` і поділ процесів; доручено крок 1.
Числа — статичні імпорти гілки `pi-hub` (`bfd0d18`), без динамічних.

## Принципи

1. Один репозиторій і одна основна гілка; пристрій не має «своєї» гілки.
2. Один код, різні параметри: роль пристрою задає профіль, а не розгалуження в коді.
3. Окремі процеси: збій одного не зупиняє ефір.
4. Кожен пристрій завантажує лише свій набір (sparse-checkout за маніфестом).
5. Застосунки й пристрої спілкуються через версійовані протоколи, а не через спільний файл БД.

## Каталоги

| Каталог | Зміст |
| --- | --- |
| `shared/` | звук, VAD, діагностика, протоколи, словники, розбір тексту, архів, доступ до БД |
| `server/` | процеси `node`, `asr` (з ботом), `panel`, `api` |
| `worker/` | вузол Whisper |
| `lab/` | лабораторія, навчання, порівняння |
| `apps/ios`, `apps/android`, `apps/miniapp` | клієнти; Mini App поки теж у цьому репозиторії (рішення власника 23.11) |
| `deploy/` | профілі, списки файлів, служби, встановлення |
| `tests/`, `docs/` | спільні |

Правило: `server`, `worker`, `lab` імпортують `shared`, але не одне одного; `shared` нікого з них. Перевіряє тест.

Чому `shared` велика: усього 159 модулів; лабораторія — 80, з них 76 спільні із сервером; `asr` (75) і `panel` (97)
ділять 50. Отже лабораторію не можна просто винести: вона перевіряє той самий розбір, що працює на Pi.
Вузол Whisper — 17 модулів, ефір — 20.

Профіль = файл у `deploy/profiles/` з процесами, залежностями, типовими параметрами й списком файлів;
секрети — лише в `.env` пристрою. Один запуск `radio345 up --profile pi`; ключі вже є: `RADIO_INPUT_DEVICE`,
`RADIO_PTT`, `RADIO_ASR_URL`, `RADIO_SPOOL`, `RADIO345_PANEL_HOST`. Бот — лише в одному профілі одночасно.

## Завантаження частин

Репозиторій у Git — близько 5 МБ, тож вибіркове завантаження економить мало місця; його сенс —
зрозумілий склад, менше зайвого на пристрої й окремі залежності (venv 126 МБ на Pi проти 1,5 ГБ на Mac).
Доступ до решти репозиторію воно **не обмежує**. `deploy/pi-files.txt` уже працює; треба узагальнити до профілів.

## Порядок (кожен крок окремо й зворотний)

1. Тест меж і список вхідних точок, без перенесення файлів.
2. Профілі та списки файлів для Pi, Mac-вузла, розробки; перевірка чистим клоном.
3. Той самий поділ процесів на Mac; `radio.py` лишається, доки новий запуск не повторить його на живому ефірі.
4. `apps/` (ios, miniapp), потім `worker/`, `lab/`, `shared/`, `server/` — по одному каталогу на коміт, без зміни логіки.
5. Android одразу в `apps/android`; версія API для застосунків.

## Ризики й відкрите

- Перенесення зламає шляхи в тестах, `.claude/rules` (`paths`), claudeSearch, CI, Xcode-проєкті; робити, коли немає інших гілок.
- `config.py` і спільна SQLite зв'язують процеси; `lab`/`server` ще спираються на одні й ті самі файли.
- `core.recognition` (MLX) досі статично досяжна з `asr` через вибір розпізнавача.
- «Відібрані» на Pi порожні; API Mini App і лабораторний виконавець на Mac не зроблено.
- Не вирішено: приватність репозиторію (Mini App поки не виносимо), доля `pi-hub`, легка модель на Pi (за вимірами придатної немає).
